# 架构与维护说明

## 分层

```text
MCP 工具 ─┐
          ├─> WorkshopService ─> 内存工作区 ──显式保存──> SQLite
Web API  ─┘          │
                     └─> 骰子、整数 GP、状态与 SRD 目录

React 管理台 ─> Web API ─> 同一 WorkshopService
```

- `mcp_server.py` 保留内部动作实现并只公开 3 个路由工具；`mcp_groups.py` 维护
  7 个大类到 42 个动作的唯一映射；`mcp_compact.py` 负责紧凑返回投影。
- `web.py` 负责 HTTP 状态码、命令白名单和静态前端托管。
- `service.py` 是规则边界。所有状态写入必须由这里进入内存工作区。
- `workspace_store.py` 负责内存草稿、线程锁、命名存档和保存冲突。
- `state.py` 定义新状态默认结构，并兼容补齐旧快照字段。
- `catalog.py` 保存可再分发的 SRD 入门数据，不与规则代码耦合。
- `spell_catalog.py` 只读加载用户法术库，负责去重、稳定 ID 和保守解析。
- `spell_rules.py` 集中保存职业别名、法术位、已知/准备与契约魔法规则表。

适配层不得直接修改工作区或 SQLite，否则 Web 和 MCP 会产生不同规则行为。

## 权威状态与标识

一个战役以 JSON 快照持久化，包含角色、物品定义、法术定义、商店、遭遇、
共享仓库和修订号。实体以 UUID 为主键，名称仅用于展示和搜索。物品定义 ID
描述“是什么”，物品栈 ID 描述“谁持有哪一批”，两者不能混用。

金额统一保存为整数 GP，不再进行币种换算；重量单位为磅。标准负重上限为 `STR * 15`。角色
生命状态由 HP、伤害、治疗和死亡豁免共同维护，`unconscious` 不能作为普通
状态直接写入。

## 外部法术目录

`spells.db` 不属于权威战役数据库。搜索时程序只返回分页摘要，读取详情时才返回
正文；角色学习或准备外部法术时，规范化快照才进入战役的 `spells`。因此已经
学习的法术在外部文件缺失或更新后仍保持不变；完整正文只进入显式保存的快照。

外部行以“来源 + 规范化名称”的 UUIDv5 作为稳定 ID。战役内已有同名 SRD
结构化法术时优先使用战役版本。自然语言解析只将单一、高置信度效果标为自动；
专注、多目标、持续、召唤和歧义效果统一降级为手动裁定。

## 多职业施法

`class_levels` 保存十二核心职业等级，`spell_repertoire` 按“法术 ID + 来源职业”
保存已知、法术书、准备或玄奥秘法状态。`spells` 仍是当前可施放法术 ID 的兼容
投影，供旧 Web 页面使用。

普通多职业法术位保存在 `spell_slots`，邪术师契约位和玄奥秘法分别保存在
`pact_slots`、`mystic_arcanum`。职业调整必须重新验证全部来源和容量；共享位
与契约位同时可用时禁止隐式选择。规则覆写必须提供原因并进入结果或保存快照。

## 草稿与保存

`CampaignStore.mutate` 的执行顺序：

1. 使用进程内 `RLock` 串行化 MCP 与 Web 修改。
2. 深复制当前草稿，在副本上执行业务规则。
3. 规则成功后替换草稿、推进草稿版本并标记 dirty。
4. 规则失败时丢弃副本，不留下部分修改。

`save_campaign` 才使用 `BEGIN IMMEDIATE`，以基准修订号更新当前战役及命名
存档。另一个进程已经保存时拒绝覆盖。加载存档要求工作区无草稿；放弃操作从
当前持久状态整体重建工作区。

## 存档迁移

旧版逐操作 before/after 快照不再继续写入。首次打开旧数据库时先通过 SQLite
Backup API 创建时间戳备份，再为每个战役创建“升级前基线”存档，删除旧操作表
并执行 `VACUUM`。备份失败时不得开始迁移，备份文件也不会自动删除。

## 扩展约束

新增写能力时应同时完成以下事项：

1. 在 `WorkshopService` 中实现校验和状态变更，并调用 `store.mutate`。
2. 在 `mcp_server.py` 增加内部动作的中文说明，明确 ID、枚举和单位，并在
   `mcp_groups.py` 将新动作加入且确保只属于一个大类。
3. 若需 Web 调用，将方法名加入 `web.py` 的 `COMMANDS` 白名单。
4. 为成功路径、规则拒绝、草稿原子性和保存冲突增加针对性测试。
5. 更新 README 的功能范围或限制，避免文档承诺超过实现。

目录数据应保留来源和许可字段。不要将规则实现绑定到来源未经确认的数据文件，
也不要导入 SRD 以外的 Product Identity 内容。

## 测试策略

- `test_service.py`：领域规则、不变量和草稿原子性。
- `test_state.py`：旧快照兼容与默认状态。
- `test_dice.py`：骰子纯函数和边界输入。
- `test_web.py`：HTTP 状态映射、命令链路和前端托管。
- `test_mcp.py`：3 个公开路由、7 个大类和 42 个动作的注册契约。
- `test_mcp_compact.py`：紧凑回执、分区查询、分页和按需正文。
- `test_workspace_store.py`：显式保存、放弃、命名存档、冲突与旧库迁移。

随机规则通过注入随机源测试。新增战斗规则时应断言结构化事件，而不只检查最终
HP，以保证 AI 可以审计骰点和规则推导过程。
